# 系统词与用户词的身份隔离（任务 5 架构评估）

> 状态：架构评估结论，不涉及 SQLite 修改。2026-07-30。

## 问题

系统 patch 词库使用数字 id（100001+ 功能词、102001+ 动词基线、103001+ 名词基线）。
用户（任何用户，不特指本机）自行录入或导入的数据也用数字自增 id。
两个来源的数字段完全可能重叠。

## 结论（逐问回答）

### 1. 数字 ID 还能否视为全局唯一？

**不能。** 数字 id 只在「单一来源内部」唯一：
- patch 内部 id 必须唯一（verify_coverage.py 仍然断言这一点）；
- 用户库内部 id 由其数据库自增保证；
- **跨来源不存在任何唯一性契约**。任何"patch id 避开某个用户的 id 段"的做法都只对那一个用户成立，
  对其他用户毫无意义。旧断言 `patch id 与 words.json 不冲突` 已删除。

### 2. 是否需要 source + id，或 spelling + pos 作为造句层身份？

两层各用一种：

- **存储/展示层**：`(source, id)` 二元组。source ∈ {`system`, `user`}。
  App 内部引用一个具体词条（展示释义、音标、难度）时必须带 source。
- **造句知识层**：`normalized_spelling + pos`（必要时 + `usage_id`）。
  语法规则不关心词条来自谁，只关心"这是哪个词的哪个词性用法"。
  normalized_spelling = 小写、去首尾空格；多词短语保留内部单空格。

### 3. 用户拥有同拼写单词时，是否只覆盖展示释义？

**是。** 覆盖规则：

| 层面 | 冲突时取谁 | 理由 |
|---|---|---|
| 释义/音标/难度/复习状态（展示层） | 用户条目优先 | 用户录的是自己的学习资料 |
| 变形字段（时态/复数拼写） | 系统优先，用户字段仅在系统缺失时兜底 | 系统形经过审计；用户可能漏填或填错 |
| 造句语法规则（可数性/动词框架/静态性等） | **只来自系统知识库** | 用户数据里根本没有这些维度，也不允许用户条目"碰巧的字段值"改变语法行为 |

### 4. 用户单词没有系统造句资料时如何处理？

**排除，不猜测。** 查找链：
`normalized_spelling + pos` → 系统造句知识库（patch/sentence/lexicon/）
- 命中 → 可参与造句（展示层再按 source 规则选释义）。
- 未命中 → 该词**不进入生成器候选池**。生成器返回机器可读原因
  （如 `excluded: no_usage_data`），UI 可提示"此词暂不支持造句"。
- 禁止回退到"按 pos 猜一个默认框架"。

## 对后续实现的约束

1. Flutter/SQLite 侧未来需要加 `source` 列（或等价判别），本轮不改。
2. 造句知识库的所有 key 一律 `spelling + pos`（见 schemas/），绝不引用数字 id。
3. 导入/备份格式中的 id 只保证来源内唯一，恢复时按 source 分桶处理。
