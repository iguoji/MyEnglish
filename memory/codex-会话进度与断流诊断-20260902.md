## 三、断流诊断：谁的问题？

### 证据（来自 `~/.codex/logs_2.sqlite`，9/2 全天 50 条重试告警）

```
WARN codex_core::responses_retry
  stream disconnected - retrying sampling request (1/5 in 188ms)...
  stream connection failed; waiting to retry
```

- 类型分布：**stream disconnected 42 次**、stream connection failed 8 次
- 重试序号：1/5 出现 26 次，只有 2 次撑到 5/5
- 单次请求输入量：最后一次统计 **单轮 352,136 tokens，累计 4355 万 tokens**

### 实测结论（2026-09-02 14:16 亲手跑的）

| 测试 | 结果 |
| --- | --- |
| 直连 `https://api.fengshao1227.com/v1/models` | HTTP 401（无 token，说明**网络通、服务活**），首字节 2.18s |
| 走 sing-box `127.0.0.1:10808` | HTTP 401，总耗时 **0.45s**（比直连快约 5 倍） |
| sing-box 监听 | 正常 LISTEN |

### 判定

| 嫌疑方 | 结论 | 理由 |
| --- | --- | --- |
| 你的网络 | ❌ 基本无辜 | 上游域名可达，代理也在跑 |
| **上游中转站** | ⚠️ 主要责任 | 服务端主动断开 SSE 流（不是连不上，是**聊到一半被掐断**），典型的中转站对长思考 / 大上下文请求做空闲回收 |
| **Codex 默认配置** | ⚠️ 放大问题 | `stream_idle_timeout_ms` 默认 5 分钟、`stream_max_retries` 默认 **5** 次；退避间隔 188ms→394ms→865ms→1.5s，**总退避才 3 秒左右**，5 次全废后 codex 就静默挂起，界面上表现为「彻底卡死、一个字都没有」 |
| **任务本身** | ⚠️ 火上浇油 | `reasoning_effort = xhigh` + 单轮 35 万 token 上下文 → 上游要算很久 → 更容易被判空闲 → 断流 → 重试 → 又传 35 万 token，死循环 |

**一句话**：上游先掐线，Codex 的重试策略太保守（只有 5 次、间隔太短）兜不住，加上超长上下文让上游思考时间变长，三者叠加。

⚠️ 特别提示：你记忆里「重试上限已从 5 调至 500」**当前并未生效**——日志里清一色 `(n/5)`，就是出厂默认值。两个可能原因：
1. 这些参数写在了 config.toml 顶层，新版 Codex **只认 provider 块内**的（顶层被忽略）；
2. 500 超过了 Codex 的硬上限 **100**，被拒绝后回落到默认 5。

## 四、解决办法（按性价比排序）

### 方案 A：加配置（最省事，治标但立竿见影）

改 `~/.codex/config.toml`，**必须写在 `[model_providers.custom]` 块内**：

```toml
[model_providers.custom]
name = "咕咕嘎嘎 - Codex"
base_url = "https://api.fengshao1227.com/v1"
wire_api = "responses"
requires_openai_auth = false
experimental_bearer_token = "sk-..."

# ↓↓↓ 新增这三行（数值都在 Codex 允许的 100 上限内）
request_max_retries = 10        # 失败的 HTTP 请求重试次数（默认 4）
stream_max_retries = 30         # SSE 流被掐断后的重连次数（默认 5，上限 100）
stream_idle_timeout_ms = 900000 # 多久没有数据才算断线（默认 300000 = 5 分钟，这里给 15 分钟）
```

改完必须**完全退出 Codex（含桌面版）再重启**，只关窗口不算。

### 方案 B：降推理强度（治本，效果最明显）

`model_reasoning_effort = "xhigh"` → 改成 `"high"` 或 `"medium"`。
xhigh 让模型思考时间成倍拉长，是断流的头号诱因。日常改代码用 high 足够。

### 方案 C：别在老会话里续命（强烈建议）

出问题的会话都已经积累了 30 万+ token 上下文。**每重试一次就要重传 35 万 token**，上游处理越久越容易断。
正确姿势：`codex` 里开新会话，把「未完成的三件事」作为新任务第一段话贴进去。

### 方案 D：让 Codex 走代理（可选）

实测代理比直连快 5 倍，sing-box 自带健康检查，链路更稳：

```bash
https_proxy=http://127.0.0.1:10808 http_proxy=http://127.0.0.1:10808 codex
```
